# Runner Core audit

- **Audit date:** 2026-08-15
- **Evidence snapshot:** working tree based on `de1305fb43f1743a708856009080ba99a67f80ba`
- **Scope:** `packages/runner_core`, plus the editor, renderer, protocol,
  validator, and backend seams that constrain Core-authored content

## Outcome

`runner_core` is large because it already contains a real deterministic game:
terrain compilation, collision, navigation, ECS stores and systems, combat,
abilities, streaming, snapshots, and replay-facing outcomes. It is not a dead
prototype and should not be replaced wholesale. Its portable analysis and test
suites are green.

The package does, however, have three changes that should happen before the
editor is allowed to create enemies, players, and projectiles:

1. Repair entity identity. Recycled integer IDs can make an old owner reference
   identify an unrelated new entity, and `destroyEntity` can recycle an ID that
   was never allocated.
2. Separate content identity from behavior. Several systems branch directly on
   `EnemyId.grojib`, `EnemyId.hashash`, or `EnemyId.unocoDemon`; a newly authored
   enemy cannot become playable just by appearing in `EnemyCatalog`.
3. Establish one validated and versioned runtime content boundary while the
   existing Dart catalogs remain authoritative. Evaluate repository source
   formats later; JSON is a candidate, not a prerequisite. The exact admitted
   gameplay revision must participate in replay admission.

The recommended migration is therefore evolutionary: preserve the simulation
and its ordered systems, fix the lifecycle hazards, introduce strict content
schemas and generators, then migrate projectiles, enemies, and characters in
vertical slices. The current Dart AST editor can remain a temporary collider
tool while that cutover is built, but it should not become the foundation for
full entity creation.

## Current architecture

| Area | Authority | Audit assessment |
| --- | --- | --- |
| Simulation loop | [`game_core.dart`](../../../packages/runner_core/lib/game_core.dart) | Explicit ordering and strong tests; too many construction and policy responsibilities |
| ECS lifecycle | [`ecs/world.dart`](../../../packages/runner_core/lib/ecs/world.dart) and stores/systems | Efficient sparse stores; unsafe identity recycling requires repair |
| Terrain/collision | `collision/terrain`, `navigation`, `track` | Mature deterministic contract; do not rewrite as part of entity authoring |
| Player content | `players/characters`, player catalogs/tuning | Typed but Dart-authored and Eloise-specific in one derived path |
| Enemy content | `enemies`, ability catalogs, level tuning | Typed catalog exists; runtime behavior is still coupled to concrete IDs |
| Projectile content | `projectiles` plus renderer/UI/backend consumers | Best first migration slice; facts are duplicated across layers |
| Abilities and gear | `abilities`, `weapons`, `accessories`, `spell_books` | Rich typed definitions; validation and injection are inconsistent |
| Outputs | snapshots and events | Clear renderer/UI boundary; mutable `GameCore` state weakens the input boundary |
| Authored terrain | JSON source -> validator/generator -> generated Dart | Correct pattern to adapt for entity authoring |

## What is already done well

- `GameCore.stepOneTick` defines a deliberate ordered pipeline and the package
  has extensive system, integration, determinism, and fresh-process replay
  coverage.
- Terrain authoring already demonstrates the desired source/generated/runtime
  separation.
- Runtime entity definitions are typed rather than unstructured maps.
- Core does not depend on Flutter or Flame.
- Catalog overrides already exist for projectiles, spell books, enemies,
  weapons, and accessories, making a future aggregate content bundle a modest
  API evolution rather than a new concept.
- The current editor working tree contains substantial safety hardening:
  transactional writes, final drift checks, typed edits/outcomes, isolated
  parsing, and scalar collider patches.

## Evidence caveat

The repository already had 59 modified or untracked paths before these audit
documents were added, including ongoing editor hardening and untracked editor
strategy/audit documents. This report audits that working tree because it is the
closest representation of the intended future editor. It does not claim those
changes are committed or complete, and it does not modify production source.
